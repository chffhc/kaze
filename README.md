# Kaze

Kaze 是一套参照 NyanPass 的功能设计、从零实现的端口转发系统,由面板、节点端和 Web 界面三部分组成,全部用 Go 编写,编译产物是不依赖 CGO 的单文件二进制。

管理员在面板里建"设备组"并把机器对接进来,用户在界面上建转发规则,面板把规则下发给节点;流量从入口节点进来,可以直接转发到目标,也可以经加密隧道送到出口节点再转发。面板负责多用户、流量配额、套餐与计费、节点探针。

本项目是独立实现,没有使用 NyanPass 的任何代码,隧道协议也与它不兼容(两者的节点不能混用)。

## 目录

```
cmd/kaze-panel     面板
cmd/kaze-node      节点端(入口与出口是同一个程序,角色由对接令牌所属的设备组决定)
cmd/kaze-bench     压测工具(目标服务端 + TCP 吞吐 / 建连速率 / UDP 回显)
internal/proto     面板与节点之间的控制协议(JSON over WebSocket)
internal/relay     转发核心:splice 零拷贝、令牌桶限速、负载均衡、UDP 会话、首包嗅探
internal/tunnel    隧道:tcp / tls / ws / wss 传输层、鉴权、yamux 多路复用、UDP 加密
internal/node      节点端逻辑:配置收敛、流量上报、探针、诊断
internal/panel     面板:SQLite、REST API、节点 Hub、计费、内嵌 Web 界面
scripts/           build.sh、e2e.py、systemd 单元
dist/              已编译好的 linux/amd64 与 linux/arm64 二进制
docs/screenshots/  界面截图
```

## 快速开始

编译(需要 Go 1.26 以上,由依赖库决定;`dist/` 里已有编译好的版本,可跳过):

```bash
bash scripts/build.sh
```

启动面板:

```bash
mkdir -p /opt/kaze && cp dist/kaze-panel-linux-amd64 /opt/kaze/kaze-panel
mkdir -p /opt/kaze/dist && cp dist/kaze-node-linux-* /opt/kaze/dist/
cd /opt/kaze && ./kaze-panel -listen 127.0.0.1:8080 -data ./data -dist ./dist -trust-proxy
```

首次启动会创建管理员 `admin`,随机密码打印在日志里,同时写入 `data/admin-initial-password.txt`(也可以用 `-admin-pass` 指定)。面板本身只提供 HTTP,请在前面放 Caddy 或 Nginx 提供 HTTPS 并反向代理,反代需要支持 WebSocket。Caddy 的配置只要一行:

```
panel.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

`-trust-proxy` 只应在面板位于反向代理之后时开启,否则访客可以伪造来源 IP 绕过登录限流。长期运行可用 `scripts/kaze-panel.service`,或者 `docker compose up -d`。

登录后的操作顺序是:在"站点设置"里填面板对外地址;在"设备组"里新建入口组(需要隧道时再建出口组);点"对接",把命令复制到机器上以 root 运行;在"套餐"里建套餐,或在"用户"里直接给用户设置额度;之后用户就可以建规则了。

对接命令形如:

```bash
bash <(curl -fsSL https://panel.example.com/install.sh) -u https://panel.example.com -t 对接令牌
```

脚本会下载节点端、写入 systemd 服务并启动。可选参数有 `-n 名称`(同机多开)、`--port`(出口隧道端口)、`--connect-host`(出口供入口连接的地址,专线填内网 IP)、`--bind`、`--uninstall`,环境变量 `OPTIMIZE=1` 会写入一组常用的内核网络参数。日志用 `journalctl -fu kaze-node` 查看。

卸载时传入安装时相同的实例名（默认 `kaze-node`）。脚本核对安装标记和当前 systemd 服务文件后才会停服务，只清理节点程序、环境文件、节点状态及其临时文件、安装标记和该服务文件。实例目录有其他内容时保留；共享的内核参数文件不会随实例删除。

旧版安装没有归属标记，或服务文件已手工改动时，脚本会拒绝覆盖或卸载。请先备份状态、环境和服务文件，用 `systemctl cat <实例名>.service` 核对实际路径；确认后手工处理旧实例，或选择未使用的新实例名。不要伪造标记来强制卸载。

## 功能

转发方面支持 TCP、UDP 和 TCP+UDP 规则;入口直出(专线场景)或经出口隧道;多目标的轮询、随机、最小连接数、按来源 IP、主备五种均衡策略,带被动故障摘除;PROXY protocol v1/v2,经隧道时同样能把访客真实 IP 传到目标;批量导入规则;链路诊断(各节点测量到下一跳的建连耗时)。

隧道的传输层有 tls、wss、ws、tcp 四种。出口组内多台机器按最小连接数均衡并自动故障转移,可以再指定一个故障转移组。多路复用开启后新连接不需要重新握手。UDP 默认走与隧道同端口的原生 UDP 通道(AES-256-GCM,每包开销 32 字节),也可以改成 UDP over TCP。CDN 模式下出口监听明文 WebSocket 供 CDN 回源。

限制方面有规则级和用户级两层限速、连接数、来源 IP 数,都在入口执行,各入口独立计算,同一用户在同一入口的所有规则共享用户级额度。入口组可以配置端口范围、直出策略、可用出口、屏蔽 HTTP/TLS/SOCKS 协议、SNI/Host 黑白名单、禁用 UDP。默认拒绝把流量转发到内网和本机地址,需要时在设备组里打开。

面板方面有注册登录、用户管理、流量配额与到期时间、套餐商城、余额、订单、兑换码(余额型和套餐型)、自动续费、易支付在线充值、公告、全站统计和用量排行;节点探针显示 CPU、内存、负载、带宽、连接数。

计费口径:流量只由入口上报,用户扣除量 = 实际流量 ×(入口倍率 + 出口倍率),直出只计入口倍率。上报带序号和确认,面板短暂不可用时不会丢也不会重复计。

## 与 NyanPass 的差异

下面这些 NyanPass 有而 Kaze 没有做:WebSSH 与远程命令执行、节点端在线升级(这两项是出于安全考虑刻意不做,拿到面板管理员权限不应等于拿到所有节点的 root)、TLS 入站与基于 SNI 的端口复用分流、反向隧道(内网穿透)、链式多跳出口、utls 指纹伪装、http 伪装传输层、USDT 类支付网关、MySQL 与 PostgreSQL、用户自带出口、规则分组。

数据库只支持 SQLite(WAL 模式),适合中小规模站点;用户和规则数很大时需要换库,目前没有实现。

## 性能

"与 NyanPass 同性能"这一点没有办法验证:NyanPass 是闭源的授权软件,拿不到节点端来做对比测试。下面是 Kaze 自己的实测数据,测试方法和工具都在仓库里,你可以在自己的机器上和 NyanPass 跑同样的测试来比较。

测试环境是一台 2 核虚拟机(AMD Ryzen 7 7735HS),面板、入口、出口、目标和压测客户端全部跑在这一台机器上走本机回环,所以数字反映的是每字节的 CPU 开销,不是真实网络下的吞吐;5 个进程挤在 2 个核上,隧道模式的结果偏保守。

| 场景 | TCP 吞吐(4 并发) | 新建连接速率(16 并发) | 首字节延迟 p50 / p99 |
|---|---|---|---|
| 直连目标(基准) | 70.9 Gbps | 18650 /秒 | 0.74 / 3.39 ms |
| 入口直出 | 47.5 Gbps | 9620 /秒 | 1.61 / 3.25 ms |
| TLS 隧道 + 复用 | 7.9 Gbps | 6596 /秒 | 2.35 / 4.45 ms |
| WS 隧道 + 复用 | 12.7 Gbps | 6653 /秒 | 2.33 / 4.42 ms |

UDP 回显(1200 字节报文,2 并发):直出约 6.7 万 pps,经隧道的原生 UDP 通道约 4.2 万 pps,丢包率 0.02% 到 0.03%。

直出走的是 `splice(2)` 内核态零拷贝,数据不进用户态,这是它接近基准的原因;开了限速或入站嗅探屏蔽的规则会退回带缓冲池的用户态拷贝。TLS 隧道的瓶颈是两端的 AES-GCM 加解密加上复用层,单核大约能跑 1 GB/s。如果线路本身可信(专线),把出口组的传输层设成 tcp 可以让隧道也接近直出的开销。

自己复测:

```bash
./kaze-bench server -l :9000                          # 在目标机器上
./kaze-bench tcp  -a 入口IP:规则端口 -c 8 -d 10s -m down
./kaze-bench conn -a 入口IP:规则端口 -c 64 -d 10s
./kaze-bench udp  -a 入口IP:规则端口 -c 4 -d 5s
```

## 安全设计

入口与出口之间用设备组的预共享密钥鉴权:每条隧道连接的开头是一个 HMAC-SHA256 前导帧。TLS 类传输层下,HMAC 里绑定了本次 TLS 会话的导出密钥,抓到的前导帧换一条连接就失效;明文传输层(tcp、ws)下改为校验时间戳和一次性随机数,节点的时钟用面板时间校准。出口证书由面板生成自签名证书并下发,入口不走 CA,而是固定校验证书的 SHA-256 指纹。

入口在隧道里只发送规则号,转发目标由出口按面板下发的规则表决定。这样即使入口机器被攻破,也不能把出口当成任意目标的开放代理。

密码用 PBKDF2-SHA256(20 万轮)存储;登录、注册、兑换码和用户写操作都有限流;修改密码会让其他设备上的登录失效;对接令牌放在只有 root 可读的环境文件里,不出现在进程命令行中。

需要知道的限制:ws 和 tcp 传输层的载荷不加密,只适合专线或外面另有加密的场景(CDN 模式下由 CDN 提供 TLS);节点到面板的连接安全依赖面板的 HTTPS,生产环境不要用明文 HTTP 对接。

## 测试

```bash
go test ./...                       # 隧道与节点的单元、集成测试
bash scripts/build.sh && mkdir -p /tmp/kz && for b in panel node bench; do cp dist/kaze-$b-linux-amd64 /tmp/kz/kaze-$b; done
python3 scripts/e2e.py /tmp/kz      # 端到端:起面板 + 入口 + 两个出口,跑完整流程并压测
```

端到端脚本覆盖 25 项检查:登录与权限、建组与对接、兑换码与购买套餐、端口分配与冲突、三种线路的 TCP/UDP 转发、链路诊断、按倍率计费、流量用尽停机与恢复、暂停与删除、用户级限速、面板重启后节点重连且期间转发不中断。

没有覆盖到的部分:易支付回调只做了代码实现,没有接真实网关联调;CDN 模式和故障转移组没有在真实多机环境下测过;没有做过长时间、大连接数的稳定性测试。上线前建议先在小范围内跑一段时间。

## 使用须知

端口转发和隧道本身是中性的网络工具,但用它做什么要符合你所在地区的法律和服务器提供商的条款。对外提供收费中转服务通常还涉及经营资质,请自行确认。
