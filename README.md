# Kaze

Kaze 是一套参照 NyanPass 的功能设计、从零实现的端口转发系统,由面板、节点端和 Web 界面三部分组成,全部用 Go 编写,编译产物是不依赖 CGO 的单文件二进制。当前版本 1.1.0。

管理员在面板里建"设备组"并把机器对接进来,用户在界面上建转发规则,面板把规则下发给节点;流量从入口节点进来,可以直接转发到目标,也可以经加密隧道送到出口节点再转发。面板负责多用户、流量配额、套餐与计费、节点探针。

本项目是独立实现,没有使用 NyanPass 的任何代码,隧道协议也与它不兼容(两者的节点不能混用)。

## 目录

```
cmd/kaze-panel     面板
cmd/kaze-node      节点端(入口与出口是同一个程序,角色由对接令牌所属的设备组决定)
cmd/kaze-bench     压测工具(目标服务端 + TCP 吞吐 / 建连速率 / UDP 回显,支持 TLS)
internal/proto     面板与节点之间的控制协议(JSON over WebSocket)
internal/relay     转发核心:splice 零拷贝、令牌桶限速、负载均衡、UDP 会话、首包嗅探
internal/tunnel    隧道:tcp / tls / ws / wss / http 传输层、鉴权、多路复用、UDP 加密、指纹、反向隧道
internal/node      节点端逻辑:配置收敛、TLS 入站与 SNI 分流、链式转发、流量上报、探针、诊断
internal/panel     面板:SQLite 与结构迁移、REST API、节点 Hub、计费、内嵌 Web 界面
scripts/           build.sh、三个端到端自测脚本、界面交互自测脚本、systemd 单元
dist/              已编译好的 linux/amd64 与 linux/arm64 二进制
docs/screenshots/  界面截图
```

## 快速开始

编译(需要 Go 1.26 以上,由依赖库决定;`dist/` 里已有编译好的版本,可跳过):

```bash
bash scripts/build.sh
```

启动面板:

```bash
mkdir -p /opt/kaze && cp dist/kaze-panel-linux-amd64 /opt/kaze/kaze-panel
mkdir -p /opt/kaze/dist && cp dist/kaze-node-linux-* /opt/kaze/dist/
cd /opt/kaze && ./kaze-panel -listen 127.0.0.1:8080 -data ./data -dist ./dist -trust-proxy
```

首次启动会创建管理员 `admin`,随机密码打印在日志里,同时写入 `data/admin-initial-password.txt`(也可以用 `-admin-pass` 指定)。面板本身只提供 HTTP,请在前面放 Caddy 或 Nginx 提供 HTTPS 并反向代理,反代需要支持 WebSocket。Caddy 的配置只要一行:

```
panel.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

`-trust-proxy` 只应在面板位于反向代理之后时开启,否则访客可以伪造来源 IP 绕过登录限流。面板仅信任列在 `-proxy-cidrs`（环境变量 `KAZE_PROXY_CIDRS`）中的直接代理，默认仅回环地址。代理必须在 `X-Forwarded-For` 末尾追加实际对端或覆盖该请求头。Docker 环境若需要真实 IP，请显式设置 `KAZE_TRUST_PROXY=1` 并填写面板实际看到的代理地址 CIDR。长期运行可用 `scripts/kaze-panel.service`,或者 `docker compose up -d`。

登录后的操作顺序是:在"站点设置"里填面板对外地址;在"设备组"里新建入口组(需要隧道时再建出口组);点"对接",把命令复制到机器上以 root 运行;在"套餐"里建套餐,或在"用户"里直接给用户设置额度;之后用户就可以建规则了。

对接命令形如:

```bash
bash <(curl -fsSL https://panel.example.com/install.sh) -u https://panel.example.com -t 对接令牌
```

脚本会下载节点端、写入 systemd 服务并启动。可选参数有 `-n 名称`(同机多开)、`--port`(出口隧道端口)、`--rev-port`(入口的反向隧道端口)、`--connect-host`(对端连接本机用的地址,专线填内网 IP)、`--bind`、`--uninstall`,环境变量 `OPTIMIZE=1` 会写入一组常用的内核网络参数。日志用 `journalctl -fu kaze-node` 查看。

卸载时传入安装时相同的实例名（默认 `kaze-node`）。脚本核对安装标记和当前 systemd 服务文件后才会停服务，只清理节点程序、环境文件、节点状态及其临时文件、安装标记和该服务文件。实例目录有其他内容时保留；共享的内核参数文件不会随实例删除。

旧版安装没有归属标记，或服务文件已手工改动时，脚本会拒绝覆盖或卸载。请先备份状态、环境和服务文件，用 `systemctl cat <实例名>.service` 核对实际路径；确认后手工处理旧实例，或选择未使用的新实例名。不要伪造标记来强制卸载。

## 功能

转发方面支持 TCP、UDP 和 TCP+UDP 规则;入口直出(专线场景)或经出口隧道;多目标的轮询、随机、最小连接数、按来源 IP、主备五种均衡策略,带被动故障摘除;PROXY protocol v1/v2,经隧道(包括多跳)时同样能把访客真实 IP 传到目标;批量导入规则;链路诊断(各节点依次测量到下一跳的连通情况)。

隧道的传输层有 tls、wss、http、ws、tcp 五种。出口组内多台机器按最小连接数均衡并自动故障转移,可以再指定一个故障转移组。多路复用开启后新连接不需要重新握手。UDP 默认走与隧道同端口的原生 UDP 通道(DTLS 1.2，预共享密钥认证),也可以改成 UDP over TCP。CDN 模式下出口监听明文 WebSocket 供 CDN 回源。

限制方面有规则级和用户级两层限速、连接数、来源 IP 数,都在入口执行,各入口独立计算,同一用户在同一入口的所有规则共享用户级额度。入口组可以配置端口范围、直出策略、可用出口、屏蔽 HTTP/TLS/SOCKS 协议、SNI/Host 黑白名单、禁用 UDP。默认拒绝把流量转发到内网和本机地址,需要时在设备组里打开。

面板方面有注册登录、用户管理、流量配额与到期时间、套餐商城、余额、订单、兑换码(余额型和套餐型)、自动续费、易支付在线充值、公告、全站统计和用量排行;节点探针显示 CPU、内存、负载、带宽、连接数和反向隧道的接入情况。

计费口径:流量只由入口上报,用户扣除量 = 实际流量 ×(入口倍率 + 出口倍率),直出只计入口倍率,链式出口只取链式出口自己的倍率。上报带序号和确认,面板短暂不可用时不会丢也不会重复计。

### TLS 入站与 SNI 分流

建规则时把"入站方式"选成"TLS 入站",入口就在这个端口上完成 TLS 握手,把解密后的流量送往后面的链路。可以限定只接受哪些 SNI、校验并协商 ALPN、填自己的证书;不填证书时入口为规则自动签发自签名证书,客户端需要关闭证书校验。送到目标时可以保持明文,也可以再加密一次(回源 TLS,由最后一跳执行,协商出的 ALPN 会一路带过去)。如果声明了 h2 而回源是明文,目标需要能处理明文的 HTTP/2。

想让多条规则共用一个端口(比如 443),先由管理员在"转发规则"页建一条入站方式为"共享 TLS 端口"的规则,它只负责监听和握手;用户再建"TLS 子规则"挂到这个端口上,各自填 SNI,入口按握手时的 SNI 把连接分给对应的规则。限速、连接数和流量统计都落在子规则上。共享端口填了证书(通常是通配符证书)时,没有自带证书的子规则会用它。

入口组的"TLS 入站"设置里可以规定用户只能建 TLS 入站规则,或只能建子规则,也可以拒绝不带 SNI 的握手;配了域名白名单后,子规则的 SNI 必须在白名单内。VLESS-Reality、ShadowTLS 这类不是标准 TLS 的协议不能用 TLS 入站,它们应该用普通规则原样转发。

### 反向隧道

出口机器在内网、没有公网入站时,让它主动连到入口:入口机器对接时在命令末尾加 `--rev-port 端口`,然后在入口组的"反向隧道"里选好哪些出口组走反向(也可以选全部)。面板会把入口的地址和证书指纹下发给这些出口,出口保持若干条到入口的 TLS 连接,入口需要转发时直接在这些连接上开流。没有加 `--rev-port` 的入口机器仍按正向隧道连接出口。反向隧道固定使用 TLS 加多路复用,UDP 封装在隧道里传输。

### 链式出口

在"设备组"页新建链式出口,依次选 2 到 3 个出口组。用户把它当作一个普通出口来选,流量从入口进来后依次经过每一跳,由最后一跳连接目标。每一段用下一跳出口组自己的隧道设置,所以各段可以是不同的传输层;入口到第一跳是否复用按第一跳出口组的设置,后面各跳之间是否复用在链式出口上设置。链式出口有自己的倍率和可见范围,用户只要被授权使用链式出口本身,不需要有途经各出口组的权限。链路上 UDP 一律封装在隧道里,各跳的故障转移组不生效;入口到第一跳可以是反向隧道,后面各跳之间只能是正向连接。

### HTTP 伪装传输层与 TLS 握手指纹

出口组的传输层选"HTTP 伪装"后,入口到出口的每条连接以一次普通的 HTTP/1.1 请求和 200 响应开头,请求头和响应头里没有 Upgrade 字样,之后是加密的数据流;没有密钥的访问者只会得到一个 nginx 样式的 404。入口要等到出口的响应才开始发数据,所以建立一条隧道连接比 tls 多一次往返,开启多路复用后这个代价只在建立复用连接时付一次。它只是外观上的伪装,头部之后不是合法的 HTTP 报文体,两端之间必须直连,不能经过 CDN 或反向代理。

传输层是 tls 或 wss 时,可以在出口组里选一个"TLS 握手指纹",入口连接出口时发出的 ClientHello 会模拟对应的浏览器(chrome、firefox、safari、ios、android、edge、qq,由 utls 库提供)。反向隧道里由出口拨号时同样生效。

## 从 1.0 升级

先升级面板,再升级节点。用新的面板二进制和新的 `dist/` 替换旧文件后重启面板,它会在启动时自动迁移数据库,并在迁移前把原库存成 `data/kaze.db.v1.bak`。然后在每台节点上重新运行一遍对接命令(或者直接替换 `/opt/kaze-node/kaze-node` 后 `systemctl restart kaze-node`),节点会沿用原来的身份。

还没升级的节点可以继续跑原有的规则,流量照常计费,界面上会标出"需升级"。用到新功能的规则(TLS 入站、回源 TLS、链式出口、HTTP 伪装传输层)不会下发给旧节点,规则状态里会写明是哪台机器需要升级;等规则途经的节点都升级之后它们自动生效。迁移后的数据库不能再交给 1.0 的面板使用,需要回退时请用备份文件。

出口组的隧道密钥、证书和入口组的反向隧道证书在保存设备组时保持不变。需要更换时,在设备组的"高级编辑"里把 `tunnel_key`、`cert_pem` 或 `rev_cert_pem` 清空再保存,面板会重新生成并同步给节点;更换会让这个组现有的隧道连接重建一次。

## 与 NyanPass 的差异

下面这些 NyanPass 有而 Kaze 没有做:WebSSH 与远程命令执行、节点端在线升级(这两项是出于安全考虑刻意不做,拿到面板管理员权限不应等于拿到所有节点的 root)、USDT 类支付网关、MySQL 与 PostgreSQL、用户自带出口、规则分组、IPv6 优先的出口名单。

1.1 补上的五项功能里也有几处细节没有照搬:TLS 入站没有"整流选项"(按回源响应内容阻断)和强制空 SNI;共享 TLS 端口对所有能用该入口组的用户开放,不能再单独限定哪些用户可以挂载;ws 和 http 传输层只能设置 Host 与路径,不能自定义整段请求头和响应头。

数据库只支持 SQLite(WAL 模式),适合中小规模站点;用户和规则数很大时需要换库,目前没有实现。

## 性能

"与 NyanPass 同性能"这一点没有办法验证:NyanPass 是闭源的授权软件,拿不到节点端来做对比测试。下面是 Kaze 自己的实测数据,测试方法和工具都在仓库里,你可以在自己的机器上和 NyanPass 跑同样的测试来比较。

测试环境是一台 2 核虚拟机(AMD Ryzen 7 7735HS),面板、入口、出口、目标和压测客户端全部跑在这一台机器上走本机回环,所以数字反映的是每字节的 CPU 开销,不是真实网络下的吞吐;多跳场景下有七八个进程挤在 2 个核上,结果偏保守。

| 场景 | TCP 吞吐(4 并发) | 新建连接速率(16 并发) | 首字节延迟 p50 / p99 |
|---|---|---|---|
| 直连目标(基准) | 71.1 Gbps | 18428 /秒 | 0.75 / 3.18 ms |
| 入口直出 | 46.5 Gbps | 9408 /秒 | 1.64 / 3.35 ms |
| TLS 隧道 + 复用 | 7.5 Gbps | 6531 /秒 | 2.37 / 4.51 ms |
| WS 隧道 + 复用 | 12.3 Gbps | 6613 /秒 | 2.33 / 4.45 ms |
| TLS 隧道 + Chrome 指纹 | 7.7 Gbps | 6034 /秒 | 2.54 / 5.20 ms |
| HTTP 伪装隧道 + 复用 | 8.1 Gbps | 6246 /秒 | 2.46 / 5.02 ms |
| 反向隧道 | 8.1 Gbps | 6046 /秒 | 2.55 / 4.93 ms |
| 三跳链式出口,各跳之间不复用 | 3.3 Gbps | 1126 /秒 | 13.89 / 24.71 ms |
| 三跳链式出口,各跳之间复用 | 3.1 Gbps | 3682 /秒 | 4.19 / 7.90 ms |
| TLS 入站,直出 | 13.9 Gbps | 1976 /秒 | 7.78 / 15.66 ms |
| TLS 子规则(SNI 分流),直出 | 未测 | 2005 /秒 | 7.73 / 15.26 ms |

前四行来自 `scripts/e2e.py`,其余来自 `scripts/e2e_features.py`,是两次独立的运行;后者同时开着更多节点进程,它自己测到的基准是 69.0 Gbps、17971 连接/秒,所以后七行与前四行比较时会略微偏低。每个场景只跑了 3 秒、一次,数字之间百分之几的差别不说明问题。

另外测了两个组合的吞吐:TLS 入站再经 HTTP 伪装隧道是 6.3 Gbps,TLS 入站直出加回源 TLS 是 9.3 Gbps。1.1.0 的 UDP 回显(旧协议，1200 字节报文,2 并发):直出约 6.7 万 pps,经隧道的原生 UDP 通道约 4.0 万 pps,丢包率 0.02% 到 0.03%。

直出走的是 `splice(2)` 内核态零拷贝,数据不进用户态,这是它接近基准的原因;开了限速、入站嗅探屏蔽或 TLS 入站的规则会退回带缓冲池的用户态拷贝。加密隧道的瓶颈是两端的 AES-GCM 加解密加上复用层,单核大约能跑 1 GB/s,指纹伪装和反向隧道只影响握手,不影响传输。TLS 入站的建连速率低,是因为每条新连接都要在入口做一次完整的 TLS 握手,压测客户端也没有做会话复用。链式出口每多一跳就多一次加解密;各跳之间不复用时,每条新连接还要逐跳重新握手,所以连接多而短的业务应该打开各跳复用。如果线路本身可信(专线),把出口组的传输层设成 tcp 可以让隧道接近直出的开销。

自己复测:

```bash
./kaze-bench server -l :9000                          # 在目标机器上
./kaze-bench tcp  -a 入口IP:规则端口 -c 8 -d 10s -m down
./kaze-bench conn -a 入口IP:规则端口 -c 64 -d 10s
./kaze-bench udp  -a 入口IP:规则端口 -c 4 -d 5s
./kaze-bench tcp  -a 入口IP:TLS端口 -tls -sni app.example.com -alpn h2 -c 8 -d 10s   # TLS 入站规则
```

## 安全设计

入口与出口之间用设备组的预共享密钥鉴权:每条隧道连接的开头是一个 HMAC-SHA256 前导帧。TLS 类传输层下,HMAC 里绑定了本次 TLS 会话的导出密钥,抓到的前导帧换一条连接就失效;明文传输层(tcp、ws)下改为校验时间戳和一次性随机数,节点的时钟用面板时间校准。出口证书由面板生成自签名证书并下发,入口不走 CA,而是固定校验证书的 SHA-256 指纹。直连 TLS/WSS 在证书固定和系统 CA 模式下都要求成功导出通道绑定。旧配置中的 360 指纹使用标准 Go TLS。

入口在隧道里只发送规则号,转发目标由出口按面板下发的规则表决定,链式出口的中间跳也只按规则表把流交给固定的下一跳。这样即使入口机器被攻破,也不能把出口当成任意目标的开放代理。

反向隧道是双向认证的:出口固定校验入口组证书的指纹,入口校验出口用本组密钥生成、并绑定了这次 TLS 会话的前导帧,而且只接受名单内的出口组。出口组被移出名单或更换密钥后,它已有的反向连接会被立即断开。

HTTP 伪装传输层的加密是自己实现的记录层:每条连接的密钥由预共享密钥、入口的随机数和出口在响应里给出的随机数派生,数据用 AES-256-GCM 分记录加密,请求里的令牌带时间戳且在同一台出口上只能用一次。截获的请求和数据拿到另一台出口或等出口重启后重放,握手能过但数据解不开,不会被再转发一遍。它没有前向保密,预共享密钥一旦泄露,此前被抓到的流量可以解密;需要前向保密时请用 tls 或 wss。

复用连接上只有发起转发的一端可以开流,出口反过来向入口开的流会被直接复位。

TLS 入站规则自带的证书私钥明文存放在面板数据库里,并下发到入口节点,接口不会把私钥返回给浏览器。不填证书时用的是自签名证书,客户端关闭校验后无法防范客户端与入口之间的中间人;回源 TLS 默认也不校验目标的证书,可以在规则里打开。

密码用 PBKDF2-SHA256(20 万轮)存储;登录、注册、兑换码和用户写操作都有限流;修改密码会让其他设备上的登录失效;对接令牌放在只有 root 可读的环境文件里,不出现在进程命令行中。

需要知道的限制:ws 和 tcp 传输层的载荷不加密,只适合专线或外面另有加密的场景(CDN 模式下由 CDN 提供 TLS);节点到面板的连接安全依赖面板的 HTTPS,生产环境不要用明文 HTTP 对接。指纹伪装和 HTTP 伪装改变的只是连接的外观,出口的证书仍然是自签名的,它们不能保证连接不被识别。

## 测试

```bash
go test ./...                              # 隧道、节点、面板的单元与集成测试(含 1.0 数据库的迁移)
bash scripts/build.sh && mkdir -p /tmp/kz && for b in panel node bench; do cp dist/kaze-$b-linux-amd64 /tmp/kz/kaze-$b; done
python3 scripts/e2e.py /tmp/kz             # 基础流程:对接、购买、转发、计费、限额、限速、面板重启
python3 scripts/e2e_features.py /tmp/kz    # 1.1 的功能:HTTP 伪装、指纹、反向隧道、链式出口、TLS 入站与 SNI 分流、故障转移组
python3 scripts/e2e_upgrade.py /tmp/kz <1.0.0 二进制目录>   # 用真实的 1.0.0 面板和节点建数据,再原地升级
node scripts/ui_flow.mjs /tmp/kz           # 用无头浏览器操作规则和设备组的表单,再用接口核对保存的结果
```

三个端到端脚本分别有 26、58、33 项检查,都在本机起真实的面板和节点、用真实流量验证,结束前会检查各进程日志里没有崩溃。界面脚本有 21 项检查,需要先装 playwright-core 和它的无头 Chromium(脚本开头有命令)。单元测试和三个端到端脚本都用开启竞态检测的二进制跑过一遍,没有发现数据竞争。升级脚本需要的旧版二进制可以这样得到:`git worktree add /tmp/kaze-v1 v1.0.0`,然后在那个目录里 `go build -o <目录>/ ./cmd/...`。

没有覆盖到的部分:所有测试都在一台机器的本机回环上,没有真实的多机、跨网和 NAT 环境,反向隧道是用"出口的正向地址连不上"来模拟内网出口的;HTTP 伪装和握手指纹只验证了功能正确以及字节层面的外观(探测得到 404、ClientHello 与 Go 默认的不同并带有 SNI 和 ALPN),没有与真实浏览器的抓包对比,也没有在真实的流量识别设备前验证过效果;TLS 入站只用 Go 和 Python 的 TLS 客户端测过,没有用浏览器或代理客户端实测;易支付回调没有接真实网关联调;CDN 模式没有测过;一键对接脚本只做了语法检查和下载测试;没有做过长时间、大连接数的稳定性测试。上线前建议先在小范围内跑一段时间。

## 使用须知

端口转发和隧道本身是中性的网络工具,但用它做什么要符合你所在地区的法律和服务器提供商的条款。对外提供收费中转服务通常还涉及经营资质,请自行确认。

### 1.1.1 节点升级

原生 UDP 改用 DTLS 1.2，WS/WSS 在升级请求时鉴权，HTTP 隧道也要求验证出口的握手响应。使用这些传输时请在同一维护窗口升级面板以及整条链路的入口、出口和备用节点。滚动升级期间可先改用固定证书的直连 TLS 并启用 UDP over TCP，待两端升级后恢复原配置。更改传输会中断已有连接。启用协议或域名过滤的入口会拒绝无法审计的 UDP 数据报，以及在 3 秒内无法完成识别的 TCP 首部。
